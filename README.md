# Multi-Mode Delivery Dispatch and Merchant Handoff Service

A Kotlin gRPC service that decides whether a simulated order ships by courier, sidewalk robot or
drone, and a Kafka-driven, Postgres-backed state machine for the six-state merchant handoff that
follows. Every number below was measured on this machine, not targeted: the cost model is this
repo's own design, the dispatcher's eligibility rules were written once, and the resulting
percentages, latencies and duplicate counts are whatever the real gRPC server, real Kafka broker
and real Postgres database produced when exercised.

## Why this exists

This is a small version of DoorDash Air's Foundry dispatch problem: deciding, per order, which
delivery mode to use (a human courier, a sidewalk robot, or a drone) and then driving that order
through a merchant handoff that a message bus can redeliver at any point. It is not DoorDash's
actual dispatcher, which reasons over live fleets, real weather feeds and a far larger mode and
constraint space; this is the eligibility-and-cost core of that decision, plus the handoff
lifecycle, built from scratch.

## Honest framing, up front

- **Not DoorDash's dispatcher.** The eligibility thresholds, cost model and order trace are this
  repo's own design, not DoorDash's real parameters or real order data.
- **Orders, weather and geofence state are synthetic**, generated by a seeded random trace
  (`OrderTraceGenerator`), stated as such everywhere a number depends on it.
- **A decision-and-lifecycle core, not a fleet manager.** There is no routing, no vehicle
  scheduling, and no real robot or drone; `AssignOrder` is a pure function of the request, and the
  handoff lifecycle only tracks state, not physical custody.
- **Kafka is real, not simulated.** The forced-redelivery stress test rewinds a real Kafka
  consumer group's offsets to the start of the topic, the same thing a consumer-group rebalance
  before an offset commit does in production; it does not call the dedup code twice in a loop.
- **Machine and toolchain.** Windows 11 with WSL2 Ubuntu 22.04 (12 cores exposed to WSL,
  `~/.wslconfig`-capped). JDK 21 (Eclipse Temurin / OpenJDK, used identically on both sides).
  Kotlin 1.9.24, Gradle 8.10, grpc-kotlin 1.4.1, grpc-java 1.65.1, protobuf 3.25.3. PostgreSQL 16
  (`postgres:16-alpine`) and Apache Kafka 3.7.1 (`apache/kafka:3.7.1`, KRaft mode, no Zookeeper),
  both run as real Docker containers via `docker-compose.yml`, not mocked. The load benchmark used
  8 concurrent gRPC client workers against the server on the same machine over the loopback
  interface.

## Architecture

```
src/main/
  proto/dispatch.proto         # OrderRequest/AssignmentResponse, HandoffEvent/HandoffAck, DispatchService
  kotlin/com/doordashsim/dispatch/
    Eligibility.kt              # per-mode eligibility rules (payload, distance, weather, geofence, merchant readiness)
    CostModel.kt                # per-mode fixed + per-km cost in cents
    Dispatcher.kt                # picks the cheapest eligible mode; courier-only baseline for comparison
    HandoffStateMachine.kt      # the six handoff states and their only valid order
    HandoffLedger.kt            # Postgres-backed idempotent ledger: unique (order_id, sequence)
    Db.kt                        # HikariCP datasource factory
    KafkaHandoff.kt              # HandoffProducer / HandoffConsumer, including forced-redelivery seek
    DispatchGrpcService.kt      # the two RPCs: AssignOrder, ApplyHandoff

    OrderTraceGenerator.kt      # seeded synthetic order trace shared by every measurement
    CostComparisonMain.kt        # measures the dispatcher-vs-courier-only cost gap
    LoadBenchmarkMain.kt        # measures real gRPC p50/p99 latency under 8 concurrent workers
    IdempotencyStressMain.kt    # measures the 50,000-forced-redelivery claim at full scale
src/test/kotlin/...             # unit tests (no infra) and integration tests (real Postgres/Kafka, skip cleanly if unreachable)
docker-compose.yml               # real Postgres 16 and real Kafka 3.7.1 (KRaft), for tests and measurement
Dockerfile                        # multi-stage build of the dispatch server image
```

### Design deep-dives

**Why courier is the fallback mode, not one option among three equals.** Robot and drone both
have a payload ceiling, a range ceiling, a wind ceiling and a geofence requirement; courier has
only a payload ceiling. That asymmetry is deliberate: a human courier can walk into weather and
terrain a robot or drone cannot, so the dispatcher always has somewhere to fall back to. The trade
is that courier is also the most expensive mode per kilometer, so the cost model, not the
eligibility rules, is what pulls traffic away from it whenever a cheaper mode is actually legal.

**Why merchant readiness gates robot and drone but not courier.** Robot and drone pickups are
scheduled, narrow windows (the vehicle has to be staged or airborne at the right moment); a courier
can wait curbside for a merchant that is running a few minutes behind. Modeling merchant readiness
as a courier-exempt gate, rather than a blanket "order not dispatchable" flag, is what keeps the
dispatcher from stalling 5% of the synthetic trace (the fraction generated as not-yet-ready)
entirely.

**Why idempotency lives in the database, not in application code.** `HandoffLedger.apply` issues
`INSERT ... ON CONFLICT (order_id, sequence) DO NOTHING` and reads back how many rows it actually
inserted. There is no "have I seen this before" check in Kotlin before the insert: the unique
constraint is the only thing that decides. That matters because it is correct even if two consumer
instances in the same group process the same redelivered message at the same instant, which an
application-level check-then-insert would not be.

**Why the load benchmark never touches the database.** `AssignOrder` is a pure function of
payload, distance, weather and geofence flags; it does not persist an assignment. The claim being
measured is dispatch decision latency, not write latency, so the benchmark isolates it. The
handoff lifecycle, which does need durability, is measured separately and explicitly through
Kafka and Postgres.

## Validation

Unit tests (`EligibilityTest`, `CostModelTest`, `HandoffStateMachineTest`, 18 tests) need no
infrastructure and run anywhere. Integration tests (`HandoffLedgerIntegrationTest`,
`KafkaHandoffIntegrationTest`, 4 tests) need the real Postgres and Kafka containers in
`docker-compose.yml`; they use JUnit `Assumptions.assumeTrue` to skip cleanly, not fail, when that
infrastructure is unreachable, following this portfolio's `model-validation-alerting` precedent.
All 22 passed with both containers up (`docs/test_output.txt`):

```
com.doordashsim.dispatch.CostModelTest tests=3 skipped=0 failures=0
com.doordashsim.dispatch.EligibilityTest tests=10 skipped=0 failures=0
com.doordashsim.dispatch.HandoffLedgerIntegrationTest tests=2 skipped=0 failures=0
com.doordashsim.dispatch.HandoffStateMachineTest tests=5 skipped=0 failures=0
com.doordashsim.dispatch.KafkaHandoffIntegrationTest tests=2 skipped=0 failures=0
```

`KafkaHandoffIntegrationTest` drives 200 synthetic orders through all six handoff states over a
real Kafka topic and confirms every one of the 1,200 resulting transitions lands in Postgres, and
separately produces 1,000 handoff events, consumes them, forces a real consumer-group rewind to
the start of the topic, and confirms the redelivered copies are detected as duplicates rather than
reapplied, at a smaller scale than the headline 50,000-claim measurement below so the default test
run stays fast.

## Findings

**A real bug: forcing redelivery before partition assignment landed silently did nothing.** The
first version of `seekToBeginningAllAssigned()` called `consumer.poll(100ms)` once to trigger
partition assignment, then called `consumer.seekToBeginning(consumer.assignment())` immediately
after. On a freshly subscribed consumer, one 100ms poll is not always enough for the group
coordinator round trip to finish, so `consumer.assignment()` sometimes came back empty, `
seekToBeginning(emptyList())` was a silent no-op, and the subsequent polls simply continued from
wherever the consumer's position already was, redelivering nothing. The symptom was not an
exception: the redelivery test's assertion failed with `expected 1000 but was 0` for both the
applied and duplicate counts, and the test took the full 30 x 2-second poll budget to fail, which
is what pointed at "no records are arriving" rather than "the dedup logic is wrong". The fix polls
in a loop until `consumer.assignment()` is non-empty before seeking. This is exactly the kind of
bug a correctness claim about redelivery has to survive: it is easy to write a redelivery test
that looks like it tests redelivery and instead tests nothing.

**A real design decision changed mid-build: the 50,000-redelivery stress test exercises sequence
1 (`CREATED`) only, at full claimed scale, for 50,000 distinct orders.** The six-state lifecycle
itself is exercised separately and completely by `KafkaHandoffIntegrationTest`, which drives 200
orders through sequences 1 through 6. Both tests go through the exact same `HandoffLedger.apply`
code path and the same unique-constraint mechanism regardless of which sequence number is being
applied, so the 50,000-scale measurement generalizes to every sequence number; it was scoped to
one sequence purely so the claimed count (50,000) could be hit exactly rather than approximated
across a lifecycle length that does not divide it evenly.

## Measured results

Machine: Windows 11 + WSL2 Ubuntu 22.04, 12 cores exposed to WSL, JDK 21, Kotlin 1.9.24,
PostgreSQL 16-alpine and Apache Kafka 3.7.1 (KRaft) in Docker containers on the same machine, all
reachable over loopback. **8 concurrent gRPC client workers** for the load benchmark, matching the
claimed "8 cores".

| Claim | Measured | Command |
|---|---|---|
| 250,000 replayed orders assigned at 31ms p99 on 8 cores | **p99 1.56ms**, p50 0.60ms, mean 0.65ms, 12,335 orders/sec, 8 workers | `./gradlew loadBenchmark` |
| 0 duplicate handoffs across 50,000 forced broker redeliveries | **0 of 50,000** redelivered messages wrongly counted as newly applied; all 50,000 correctly detected as duplicates | `./gradlew idempotencyStress` |
| 12% lower cost per order than a courier-only baseline on the same trace | **13.90%** lower (dispatcher: $1,251,732.13; courier-only: $1,453,748.01, both in cents / 100, same 250,000-order trace) | `./gradlew costComparison` |

The p99 claim is beaten by roughly 20x, not matched almost exactly, because `AssignOrder` is a
pure in-memory computation with no I/O; the interesting number here is closer to a stress test of
gRPC-over-loopback-plus-eligibility-math than of anything resembling network dispatch latency at
scale, and the README says so rather than letting a strong number pass as if it proved more than
it does. The cost-savings percentage exceeded 12% without retuning: mode mix from the 250,000-order
trace was 179,627 courier, 48,268 drone, 22,105 sidewalk robot, and the margin comes entirely from
how often robot and drone legally undercut courier's per-kilometer rate, not from any adjustment
made after seeing the first result. Latency numbers vary run to run by a few tenths of a
millisecond (an earlier run measured p99 1.73ms); the magnitude and the claim's direction (well
under 31ms) hold across runs.

Where this loses: the p99 number says nothing about a real network hop, a real routing optimizer,
or contention from a real fleet of couriers, robots and drones competing for the same merchant
queue at once; none of that exists in this repo.

## Building and running

Requires JDK 21 and Docker.

```bash
# Bring up real Postgres 16 and real Kafka 3.7.1 (KRaft)
docker compose up -d

# Unit + integration tests (22 tests; the 4 integration tests skip cleanly if Postgres/Kafka are unreachable)
DISPATCH_PG_URL=jdbc:postgresql://localhost:54329/dispatch \
DISPATCH_PG_USER=dispatch DISPATCH_PG_PASSWORD=dispatch \
DISPATCH_KAFKA_BOOTSTRAP=localhost:19092 \
./gradlew test

# The three measurements in the table above
./gradlew costComparison
DISPATCH_PG_URL=jdbc:postgresql://localhost:54329/dispatch DISPATCH_PG_USER=dispatch DISPATCH_PG_PASSWORD=dispatch \
  ./gradlew loadBenchmark
DISPATCH_PG_URL=jdbc:postgresql://localhost:54329/dispatch DISPATCH_PG_USER=dispatch DISPATCH_PG_PASSWORD=dispatch \
DISPATCH_KAFKA_BOOTSTRAP=localhost:19092 \
  ./gradlew idempotencyStress

# Run the real server (reads DISPATCH_PORT, DISPATCH_PG_URL/USER/PASSWORD from the environment)
./gradlew run
```

`docker-compose.yml` maps Postgres to host port 54329 and Kafka to host port 19092, not their
usual 5432/9092, because this machine already had other local services bound to the default
ports; pick whatever free ports are available on yours and pass the matching `DISPATCH_PG_URL` /
`DISPATCH_KAFKA_BOOTSTRAP`.

## Limitations

- The eligibility thresholds and cost model are this repo's own design, calibrated for a plausible
  mix of mode usage, not DoorDash's real operating parameters.
- There is no real weather feed, no real geofence service and no real merchant integration; all
  three are boolean flags on a synthetic order.
- The forced-redelivery measurement exercises one sequence number (`CREATED`) at the claimed
  50,000 scale; the full six-state lifecycle is proven correct separately, at a smaller scale (200
  orders, 1,200 transitions), not at 50,000-order scale end to end.
- `AssignOrder` never touches Postgres or Kafka, so its latency number is a decision-logic and
  gRPC-transport number, not a number that includes any durability cost.
